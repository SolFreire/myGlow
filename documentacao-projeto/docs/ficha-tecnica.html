01

Plataforma e linguagem

Swift como linguagem e SwiftUI como framework de UI — caminho nativo recomendado pela Apple para apps novos, com integração direta com SwiftData, Foundation Models e PhotosUI. Xcode cobre build, teste e distribuição.

A decisão mais importante do projeto é a versão mínima de iOS, porque ela trava o que fica disponível para a IA (próxima seção). Duas rotas:

Rota A — iOS 26 como mínimo

Acesso direto ao Foundation Models framework, sem lógica condicional. Em troca, exclui usuárias em versões ou dispositivos mais antigos.

Rota B — iOS 18 (ou anterior) como mínimo, com detecção de recurso

Cadastro, trilha guiada, câmera, edição e compartilhamento funcionam em versões mais antigas. A sugestão por IA verifica SystemLanguageModel.availability em tempo de execução e cai para conteúdo estático/regras pré-definidas quando o recurso não está disponível.

02

IA generativa on-device — Foundation Models

É o componente mais específico do produto: usar o inventário de maquiagens cadastrado para que o personagem sugira técnicas alternativas — por exemplo, na ausência de delineador líquido, orientar como fazer o mesmo efeito com lápis.

O que é

Framework nativo da Apple, introduzido no iOS 26, que expõe a apps de terceiros o mesmo modelo de linguagem on-device usado pela Apple Intelligence.

Peças principais da API

  • SystemLanguageModel — ponto de acesso ao modelo; é preciso checar availability (.available / .unavailable(reason)) antes de usar.
  • LanguageModelSession — mantém contexto e histórico da conversa; inicializada com instruções, guardrails e ferramentas.
  • @Generable / @Guide — pedem saída estruturada (JSON tipado) em vez de texto livre, útil para retornar algo como { tecnica, substituicoes, passoAPasso }.
  • Tool calling — o modelo chama funções Swift customizadas (ex.: consultar os itens cadastrados) via o protocolo Tool, sem precisar reinjetar o inventário inteiro a cada prompt.
  • streamResponse() — resposta em streaming, útil para a sensação de personagem falando em tempo real durante o tutorial.

Requisitos e limitações

  • Exige iOS 26+ e hardware compatível com Apple Intelligence — na prática, iPhone 15 Pro/Pro Max ou mais recente (A17 Pro ou superior), com Apple Intelligence habilitada nas configurações.
  • Um guardrail de conteúdo da Apple é sempre aplicado e não pode ser desativado.
  • Roda majoritariamente on-device; prompts mais complexos podem usar Private Cloud Compute (infraestrutura própria da Apple).
  • Ainda pode carregar rótulo de API em evolução — vale conferir a documentação da versão de Xcode usada pelo time.

Novidade WWDC26

A Apple abriu o Foundation Models framework para provedores de LLM de terceiros (Gemini, Claude/Anthropic incluídos) via um protocolo público (LanguageModel / LanguageModelExecutor). O mesmo código de LanguageModelSession passa a funcionar com outro provedor por trás — o que abre a estratégia de usar on-device como padrão e um provedor de nuvem como fallback em dispositivos sem Apple Intelligence, mantendo a mesma interface de código. Isso exige guardar a chave de API fora do app, ou seja, um pequeno backend/proxy (seção 8).

Para o inventário de maquiagens, progresso na trilha e preferências da usuária.

SwiftData também integra de forma mais direta com CloudKit, o que facilita a sincronização opcional entre dispositivos (seção 8).

Cadastro por seleção, não por digitação

Decisão do time: o cadastro não é um campo de texto livre — o usuário seleciona o item numa lista ilustrada de opções pré-definidas (catálogo com ícone/ilustração por item, curado pelo time de design; hoje desenhado como arrastar o item até a cesta da categoria correspondente, seção 6). Isso muda o que a camada de dados precisa tratar:

  • Não existe validação de texto livre (campo vazio, caracteres inválidos, nome mal formatado) — essa classe inteira de erro não ocorre, porque a entrada já vem de uma seleção fechada e válida.
  • O catálogo ilustrado (nomes, ícones, associação com subcultura/categoria) é conteúdo estático — vive como asset/JSON no bundle do app, não como dado gerado pelo usuário, e é responsabilidade do design, não da camada de persistência.
  • A única validação que ainda faz sentido no cadastro é de duplicidade (o mesmo item sendo arrastado/selecionado duas vezes) — e mesmo essa pode ser resolvida na própria UI (item já cadastrado fica "desabilitado" no catálogo) em vez de uma checagem no código de persistência.
04

Câmera, mídia e edição de imagem

Captura da foto final

  • PhotosPicker (PhotosUI) se bastar usar o app de Câmera do sistema ou escolher uma foto já existente.
  • AVFoundation / AVCaptureSession se for necessária uma tela de câmera customizada — por exemplo, com o espelho do salão já visível durante a captura.

Edição pós-captura

  • Posicionamento dos stickers, em tela: SwiftUI puro resolve — um ZStack com a foto base e cada sticker como uma Image, posicionado por gestos (DragGesture + MagnificationGesture + RotationGesture combinados). Não precisa de Core Image pra isso; é composição de views, não processamento de pixel.
  • Achatar a composição final (pra salvar/compartilhar): ImageRenderer (SwiftUI, iOS 16+) renderiza a própria hierarquia de views direto para um UIImage, sem duplicar a lógica de posição numa segunda camada. Alternativa mais manual: UIGraphicsImageRenderer (Core Graphics), desenhando cada camada com as transformações de posição/rotação/escala.
  • Core Image / CIFilter só entra se, além dos stickers, algum filtro de cor/tom ou blend mode for adicionado depois (brilho tipo "screen", granulado, saturação). Para colagem pura de elementos estáticos, sem processamento de pixel, é mais maquinário do que o necessário.
  • Metal fica para depois — só necessário se entrarem efeitos mais elaborados (partículas, distorção); overlays estáticos não precisam disso na primeira versão.
05

Compartilhamento e salvamento local

  • ShareLink (SwiftUI, encapsula o UIActivityViewController) para compartilhar a foto editada em outros apps.
  • PhotosUI / PHPhotoLibrary para salvar no rolo da câmera, com o pedido de permissão correspondente.

No Info.plist: NSCameraUsageDescription, NSPhotoLibraryAddUsageDescription (e NSPhotoLibraryUsageDescription se também for necessário ler fotos existentes).

06

Interface, navegação e narrativa dos personagens

Interação de cadastro — arrastar maquiagem para a cesta

O design pediu, na tela de cadastro, uma interação de arrastar cada item até uma cesta correspondente ao tipo dela (batom, delineador, etc.). É um drag-and-drop de UI — sem física, colisão ou câmera de jogo — então não precisa de SpriteKit: as APIs nativas do SwiftUI já cobrem isso.

  • .draggable(_:) + .dropDestination(for:action:) (SwiftUI, iOS 16+) — caminho mais rápido, baseado no protocolo Transferable; menos controle sobre a prévia do arraste e o feedback visual durante o gesto.
  • DragGesture manual + checagem de sobreposição de frame/GeometryReader — mais código, mas controle total: cesta destacando ao passar o item por cima, animação de mola (.spring()) se soltar fora do alvo, e .sensoryFeedback (iOS 17+) para o "click" tátil no momento em que o item entra na cesta.

Para o nível de capricho que o time de design está pedindo (feedback visual/tátil no drop), a rota de DragGesture manual tende a entregar o resultado esperado; .draggable/.dropDestination é a opção mais rápida se o visual padrão do sistema já bastar.

07

Gamificação e progresso

O progresso e as conquistas podem ser modelados diretamente em SwiftData (entidades de conquistas, maquiagens completadas, subculturas exploradas). GameKit / Game Center é opcional e vale a pena se quiser conquistas e ranking padronizados pela Apple sem construir essa infraestrutura do zero.

08

Sincronização entre dispositivos e backend

CloudKit é a forma mais simples de sincronizar o cadastro e o progresso entre os dispositivos da mesma usuária via iCloud, sem manter servidor próprio — e integra bem com SwiftData (.modelContainer(for:cloudKitDatabase:)).

Um backend próprio só entra em cena se a IA em nuvem (seção 2) for usada como fallback: nesse caso, um proxy simples (Cloudflare Workers, Vercel Functions ou AWS Lambda) guarda a chave do provedor de LLM e repassa a chamada — a chave nunca deve ficar embutida no app.

Para o escopo descrito hoje (cadastro, tutorial, IA on-device, foto, compartilhar), nenhum backend próprio é necessário.

Roadmap — v2 e além

Prioridade para a v2 — Create ML no cadastro

Decisão do time: se der tempo, a segunda versão estável explora Create ML para acelerar o cadastro — a usuária fotografa o item de maquiagem e o app sugere automaticamente o tipo/categoria (batom, delineador, sombra etc.), em vez de preencher tudo manualmente.

O que isso envolve, para dimensionar o esforço quando chegar a hora:

  • Dado de treino — um conjunto de fotos rotuladas por categoria de item (quanto mais variado em ângulo, marca e embalagem, melhor a generalização). Tipicamente é o maior custo do recurso, não o código.
  • Treinamento — Create ML oferece o app visual (sem código, arrasta o dataset e treina um classificador de imagem) ou o framework em Swift/Playground (mesmo processo, programático e versionável). Para categorias de maquiagem, o app costuma bastar.
  • Integração — o modelo exporta como .mlmodel/.mlpackage e entra via Core ML + Vision (VNCoreMLRequest): a foto do cadastro passa pelo modelo, que devolve a categoria sugerida, com a usuária podendo corrigir.
  • Convive com o Foundation Models — são complementares: Create ML classifica o que é o item a partir da imagem; Foundation Models sugere a técnica a partir do inventário já cadastrado.

Vale já reservar, na v1, um ponto de extensão simples no fluxo de cadastro (ex.: um passo opcional de "fotografar o item") para a v2 plugar o classificador sem redesenhar a tela.

Mais além (sem prazo definido)

  • ARKit + RealityKit — provador de maquiagem em tempo real sobre o rosto ao vivo, caso o produto evolua da edição pós-foto para um filtro ao vivo.
  • Vision framework — detecção de pontos do rosto (olhos, lábios) para alinhar automaticamente os overlays da subcultura, em vez de posicionamento manual.

Por que isolar a IA e o Create ML atrás de protocolo: a ViewModel do Tutorial não deveria saber se a sugestão veio do modelo on-device, de um provedor de nuvem (fallback do WWDC26) ou se o item veio de cadastro manual ou classificado pelo Create ML. Isso permite trocar a implementação sem tocar em UI, e testar a ViewModel com um mock em vez de precisar de um iPhone 15 Pro rodando os testes.

protocol TechniqueSuggesting {
    func suggestTechnique(
        for step: TutorialStep,
        inventory: [MakeupItem]
    ) async throws -> TechniqueSuggestion
}

enum TechniqueSuggesterFactory {
    static func make() -> TechniqueSuggesting {
        switch SystemLanguageModel.default.availability {
        case .available:
            return FoundationModelsSuggester()
        case .unavailable:
            // troque por StaticRulesSuggester() se não quiser depender de um backend próprio
            return CloudFallbackSuggester()
        }
    }
}

MakeupItemClassifying segue o mesmo desenho: na v1, uma implementação ManualEntryClassifier (preenchimento manual mesmo); na v2, troca por CreateMLClassifier sem mexer na tela de cadastro.

Persistência: os @Model do SwiftData ficam em Core/Persistence/Models; o acesso passa por um repositório fino (MakeupInventoryRepository, ProgressRepository) em vez de @Query espalhado pelas Views — facilita trocar a fonte de dados depois (ex.: CloudKit) e testar com ModelConfiguration(isStoredInMemoryOnly: true).

Injeção de dependência: um AppEnvironment simples injetado via .environment() no root da App é suficiente para este tamanho de app — evita a complexidade de um framework de DI.

Testes: ViewModels testadas com mocks dos protocolos acima; Views cobertas por XCUITest no fluxo ponta a ponta (seção 9).

Modularização (só se o time crescer): a estrutura de pastas acima em um único target já basta para a v1. Se a equipe crescer, cada pasta de Core/ vira um Swift Package local — refactor mecânico, porque as dependências já estão isoladas por protocolo desde o início.

Por que MVVM e não TCA (The Composable Architecture)

MVVM não é "a melhor arquitetura" em termos absolutos — é a escolha certa para o formato atual deste projeto. O TCA (biblioteca de terceiros da Point-Free, baseada em State/Action/Reducer/Effect, estilo Redux/Elm) é tecnicamente mais rigoroso em alguns pontos: testa efeitos assíncronos de forma determinística — bom para o streaming do Foundation Models sem depender de tempo real —, força que toda mudança de estado passe por um único lugar, e escala bem quando várias features compõem estado entre si.

  • Ceremônia vs. tamanho do time/prazo — TCA pede modelar cada ação como caso de enum e cada tela como reducer; vale a pena com estado complexo e compartilhado entre muitas features, não para uma jornada majoritariamente linear com um time pequeno correndo pra validar a PoC e esperando as artes.
  • Curva de aprendizado e contratação — MVVM + @Observable é o padrão que a própria Apple ensina; TCA exige onboarding específico (reducers, effects, macros).
  • Dependência de terceiro — mantido pela Point-Free, não pela Apple; maduro e amplamente usado, mas é uma peça a mais fora do controle da equipe, com tempo de compilação adicional pelas macros.
  • O ponto forte do TCA já está coberto — testar efeitos assíncronos e trocar implementações de forma controlada já foi resolvido isolando IA e Create ML atrás de protocolo, sem precisar da arquitetura inteira.

Vale reconsiderar TCA se o app ganhar bastante estado cruzado entre features mais pra frente (gamificação afetando várias telas ao mesmo tempo, navegação profunda) — a migração não seria do zero, já que Core/AI isolado por protocolo entra num reducer do TCA sem precisar ser reescrito.

14

PoC do Foundation Models — para rodar em paralelo às artes

Enquanto a equipe técnica/design fecha ilustrações e animações dos personagens, dá para validar isoladamente se o Foundation Models entrega o que o produto precisa — sem depender de nenhuma tela final. É o maior risco técnico do app e o mais barato de testar cedo.

Objetivo

Responder três perguntas antes de investir na experiência completa: (1) o modelo produz sugestões de técnica corretas e no tom de cada personagem/subcultura; (2) tool calling e saída estruturada (@Generable/@Guide) funcionam de forma confiável com um inventário de itens; (3) o guardrail de conteúdo da Apple — que não pode ser desativado — não atrapalha vocabulário legítimo da estética gótica (caveira, sangue estilizado, luto, ocultismo).

Achados de um teste manual inicial (chamada crua, sem instructions/tool/saída estruturada)

Antes de montar a PoC estruturada, valeu a pena rodar LanguageModelSession().respond(to:) diretamente, só com uma pergunta em texto livre. Três achados concretos que já mudam o desenho desta PoC:

  • Conhecimento de subcultura é real, mas desigual. "How can I do a simple goth makeup" cru voltou um passo a passo correto e específico. "Gyaru" cru voltou algo genérico; só ficou preciso (contorno, técnica de aumentar os olhos) com "gyaru clássica". "New Romantic" cru foi o pior caso: o modelo entendeu como "maquiagem romântica" genérica, sem relação com a subcultura/movimento musical britânico dos anos 80 — só acertou depois de reforçar "New Romantic 80's pop". Conclusão: as instructions da sessão precisam incluir uma descrição curta de cada subcultura, para não depender de o usuário escrever a palavra-chave certa.
  • O modelo não respeita "use apenas estes itens" de forma confiável. Com um inventário limitado, o modelo generalizou bem em alguns pontos (usou corretivo como base, sem base disponível) mas mencionou produtos fora da lista (primer, pó) e forçou o uso de todos os itens mesmo quando um deles não fazia sentido (bronzer sugerido tanto pra New Romantic quanto pra gótico). Isso não se resolve só com prompt mais educado — precisa de estrutura: um campo de saída dedicado a "itens não utilizados e por quê", mais uma checagem determinística no código como rede de segurança.
  • Latência sem streaming: 4 a 5 segundos por resposta, mesmo pra um pedido simples. Confirma a necessidade de streamResponse() na tela de tutorial em vez de esperar a resposta inteira parada.

Os três testes usaram só texto livre — nenhum usou @Generable/@Guide nem a Tool de inventário. A base de conhecimento é promissora; a parte de controle/restrição — o que a saída estruturada e regras explícitas devem resolver — ainda é o próximo passo real desta PoC, não um bônus.

Critérios de sucesso

  • Sugestões plausíveis e no tom certo em pelo menos ~80% de uma bateria de ~15 prompts de teste (5 por subcultura).
  • Nenhum produto fora do inventário aparece na sugestão sem estar no campo "itens não utilizados" — motivado pelo achado acima.
  • Itens do inventário que não fazem sentido pro visual são sinalizados como não utilizados, em vez de forçados (ex.: bronzer num visual gótico).
  • A subcultura certa é reconhecida mesmo com o nome curto/ambíguo (só "new romantic", sem reforçar "anos 80"), graças ao contexto embutido nas instructions.
  • Tool calling busca corretamente o item certo no inventário mock — comparar com a injeção direta da lista (mais simples, e foi o que funcionou no teste manual) e decidir qual usar na v1.
  • streamResponse() começa a exibir texto em tempo aceitável — o teste manual sem streaming mediu 4-5s de espera "muda".
  • Nenhum prompt legítimo de maquiagem gótica é bloqueado pelo guardrail; se algum for, documentar o gatilho e ajustar o prompt/instructions.
  • O caminho de fallback (protocolo TechniqueSuggesting) troca de implementação sem mudar código de chamada.

Escopo técnico

  • Target/tela de debug isolada — sem arte, sem animação: texto do sistema, botões padrão, uma lista simples.
  • Tela de diagnóstico checando SystemLanguageModel.availability e exibindo o reason bruto quando .unavailable — já foi relatado o availability retornar .available mesmo com o download do modelo incompleto, por divergência entre idioma do Siri e do sistema.
  • Inventário mock (array Swift ou JSON, sem SwiftData/UI de cadastro ainda), com itens propositalmente ausentes em alguns casos.
  • LanguageModelSession com instructions por personagem (gótico, gyaru, new romantic) — testar se o prompt sozinho sustenta a voz.
  • Uma @Generable struct de saída (passo a passo, substituições, curiosidade) via @Guide.
  • Uma Tool simples consultando o inventário mock, validando o tool calling ponta a ponta.
  • O protocolo TechniqueSuggesting da seção 13 já plugado aqui, com uma segunda implementação-esqueleto para validar a troca sem vazar para quem consome.
  • Registro simples dos resultados (log/arquivo) para comparar respostas entre iterações de prompt.

Fora do escopo desta PoC

Arte e animação dos personagens, tela de câmera/edição final, interação de arrastar para a cesta, CloudKit, gamificação, Create ML (v2) — tudo isso segue nos trilhos já descritos nas seções anteriores.

Confirmar antes de começar — acesso a dispositivo

Foundation Models exige iOS 26+ em hardware com Apple Intelligence (iPhone 15 Pro+). Há relatos de desenvolvedores para quem o Simulator não reporta o modelo como disponível de forma confiável — a PoC deve partir do princípio de que vai precisar de um iPhone físico compatível, e isso deve ser confirmado antes de alocar tempo de desenvolvimento.

Esforço estimado: um dev, cerca de 3 a 5 dias — a maior parte tende a ir para iterar o texto das instructions/prompt até o tom ficar consistente, não para o código de integração em si.

Testes unitários com Swift Testing — prospecção

A seção 9 já apontava Swift Testing/XCTest + XCUITest; aqui está o detalhamento de onde aplicar Swift Testing especificamente, mapeado na arquitetura da seção 13.

Por que Swift Testing (para a parte unitária)

Sintaxe mais enxuta que o XCTest: @Test no lugar do prefixo test, #expect como asserção única (mostra a expressão real que falhou, sem escolher entre XCTAssertEqual/XCTAssertTrue/etc.) e #require para desembrulhar opcional interrompendo o teste se vier nil. Suporte nativo a async/await — importante porque quase toda a camada de IA e persistência é assíncrona. Testes parametrizados (@Test(arguments:)) evitam duplicar teste por variação de entrada. Tags filtram por categoria (ex.: separar o que roda em todo PR do que exige hardware real). E convive no mesmo target com o XCTest — o XCUITest continua necessário para UI e testes de performance (XCTMetric).

Onde aplicar, por camada

  • Core/AI — a resposta real do Foundation Models é não determinística, então não faz sentido testar unitariamente "o texto que o modelo gerou". Testável: a lógica de TechniqueSuggesterFactory (dado um availability mockado, escolhe a implementação certa), o mapeamento da saída @Generable para o modelo de domínio, o comportamento de erro/fallback, e a conformidade do CloudFallbackSuggester/StaticRulesSuggester ao protocolo. Testes que dependem do modelo real (útil pra acompanhar a PoC da seção 14) ficam com uma tag própria (ex.: .tags(.requiresDevice)) para não travar o CI.
  • Core/Persistence — repositórios testados contra ModelConfiguration(isStoredInMemoryOnly: true) do SwiftData; cada @Test cria seu próprio container em memória, isolamento limpo sem o setUp/tearDown compartilhado do XCTest.
  • Features/Cadastro — a lógica de "o item foi solto dentro da cesta?" só vale a pena testada como função pura, fora do gesture handler; extraída assim, é caso perfeito pra teste parametrizado com várias combinações de posição/offset.
  • Features/Tutorial — ViewModel testada com um mock de TechniqueSuggesting: estado indo de carregando → sucesso/erro corretamente, inventário repassado do jeito certo.
  • Features/Gamificacao — regras de desbloqueio de conquista são lógica pura, também ótimas para parametrização.
  • Core/Media — CameraService/PhotoLibraryService são casca fina sobre AVFoundation/PhotosUI e não compensam teste unitário direto; vale testar a lógica em torno, não a captura em si.

Fora do escopo do teste unitário

Qualidade da resposta do Foundation Models real (fica com a bateria de prompts da PoC), captura de câmera de verdade, fluxo ponta a ponta de UI (XCUITest) e testes de performance (XCTMetric, também XCTest).

Recurso extra: exit tests

Desde o Swift 6.2, Swift Testing suporta exit tests — validam código que encerra o processo (fatalError, precondition), rodando em um processo filho. Útil se algum ponto da camada de dados usar precondition para invariantes (ex.: garantir que um MakeupItem sempre tem uma subcultura associada).

Plano faseado

  • Durante a PoC (seção 14): lógica de TechniqueSuggesterFactory e validação da saída @Generable — reaproveita o trabalho da PoC diretamente.
  • Construção da v1: testes de repositório (SwiftData em memória), função pura do drop na cesta, ViewModels com mocks.
  • Hardening pré-lançamento: regras de gamificação, casos de borda, revisão de cobertura.

Estrutura de testes espelha Core/ e Features/ (ex.: MaquiagemAppTests/Core/AI/TechniqueSuggesterFactoryTests.swift), rodando em todo PR — exceto os marcados com a tag de hardware real, que rodam manualmente antes de cada release.
